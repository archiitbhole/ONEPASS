What ONEPASS already has

An audit of the working codebase against 45 requested capabilities, carried out before any of them were built. The finding that matters: two thirds of what was asked for is a composition of systems that already exist, and building them fresh would have given ONEPASS two wallets, two assistants and two privacy systems.

How to read the matrices

Every row cites a file, a route or a table. Where a row says something exists, it names where — an audit that says “already exists” without a path is an assertion, not a finding.

AFully implemented. Works today. No action beyond exposing it in the UI.
BPartially implemented. Some of the capability is real; the rest is missing. Complete it in place.
CNot implemented. Genuinely absent after a full search.
DExists under a different name. The request and the code use different vocabulary for the same thing.
EComposable from existing systems. No new engine needed — assemble what is there.

One finding that changes a design. The requested “impossible travel” detection was going to be built from IP addresses — but ONEPASS deliberately stores only ip_hash, a one-way peppered hash, so an IP here cannot be geolocated. That is a privacy property worth keeping. The detector instead computes travel speed between pass_presentations joined to venues.latitude/longitude — real scan locations, which is both more accurate and requires no third-party IP intelligence vendor.
Built as specified, with one schema change the design forced. src/lib/security/detect.ts now implements all four detectors, writing into the existing security_events table through recordSecurityEvent — no second security store, as this audit required. Implementing it exposed a gap: a presentation recorded only the organization, so a chain with branches in two cities could not be told apart from a re-scan at one counter. pass_presentations.venue_id was added (nullable — an organization-wide API key legitimately has no venue), and where a terminal names no venue the detector uses the slowest candidate pairing, so ambiguous evidence cannot manufacture a finding. 22 integration tests, most of them negative cases.

Two functions from the first draft were deleted rather than shipped: lockAccount and unlockAccount duplicated PATCH /api/admin/users/[id], which already suspends, revokes every session and audits the reason. That is exactly the duplication this audit exists to prevent, and it was caught by re-reading the audit before finishing.

05

The approval gate, answered

The seven questions the brief required before implementation resumes.

1 · What already exists

Identity, authentication, per-tenant authorization, consent, the pass and its verification, the credential trust engine, notifications, real-time delivery, the audit and security trail, and the payment rail. Fifty-nine integration tests cover the parts where a mistake is a breach rather than a bug — tenant isolation, privilege escalation, credential tampering.

2 · What is partially implemented

Security records events but does not detect them. Payments are wired to a real Razorpay adapter but running on the sandbox until keys arrive. The developer platform stores and authenticates keys but has no console. Locale is stored but nothing translates. The commerce layer has its schema and its two riskiest services and little else.

3 · What is missing

The entire user interface, and five genuinely new capabilities: splitting a bill, gifting a booking, indoor maps, parking memory, and the anomaly detector.

4 · What gets extended rather than built

Fifteen of the twenty. Parking becomes a venue kind and a capacity unit. A campus becomes an organization kind. A student becomes a credential. The concierge and the voice interface both become entry points to the one assistant. Group booking becomes collaborators on the itinerary that already exists.

5 · What genuinely needs creating

Seven tables: split_requests, split_shares, gifts, venue_maps, venue_nodes, parked_vehicles, and itinerary_collaborators. Against 45 requested features, that is the measure of how much was already there.

6 · Duplicates avoided

Twelve, listed in section 07 below.

7 · Canonical sources of truth

Fixed in section 06. Every new feature composes these; none may shadow one.

06

Canonical sources of truth

One system per capability, named. A pull request that introduces a second store for anything on this list is wrong by construction, whatever it is called.

  1. Identity
    users · user_profiles · devices — one row per person, forever
  2. Authentication
    sessions (opaque tokens, SHA-256 at rest) · lib/auth/*
  3. Authorization
    lib/authz/authorize.ts — permissions resolved per membership
  4. Consent & privacy
    consent_grants · partner_connections
  5. Pass & verification
    passes · pass_presentations · packages/pass
  6. Credentials
    credentials · credential_types · verifications
  7. Money
    transactions · payment_methods · lib/payments/provider.ts
  8. Capacity
    inventory_slots — the only thing that may be sold
  9. Booking
    bookings — every reservation, of anything, including parking
  10. Rewards
    reward_ledger — append-only; the balance is a cache of it
  11. Assistant
    the planner engine · itineraries — plans, concierge answers and voice all land here
  12. Notifications
    notifications · lib/delivery.ts
  13. Security & audit
    security_events · audit_logs · lib/audit.ts
  14. Analytics
    aggregate reads only — no per-person profile table
07

Duplicates the audit prevented

Each of these was implied by a feature request read literally, and each would have created a competing source of truth.

  • A second privacy systemPrivacy lock became a master switch over consent_grants, not a parallel permission store.
  • A second security storeThe shield writes to security_events — the same table the admin console already reads.
  • A second pass formatOffline mode uses the TOTP pass that already verifies without a network. No new QR type.
  • A second recovery pathDevice recovery extends the existing reset flow and session-generation revocation.
  • A second checkoutOne-tap checkout is one cart producing many bookings and one transaction on the existing rail.
  • A second booking engineParking reserves an inventory_slot like every other bookable thing.
  • A second itinerary systemGroup booking rooms are collaborators on itineraries.
  • A second AI assistantConcierge and voice are entry points to the one planner. Twice avoided.
  • A second locale storePer-interaction language reads user_profiles.locale with a request override.
  • A second wallet for studentsStudent status is a credential; the wallet and identity stay one.
  • A second tenant model for campusA university is an organization. Members, roles and consent are unchanged.
  • A second location systemCheck-in zones read venues.latitude/longitude, already on every venue.

Standing rule for every screen built from here. No interface may claim a payment occurred, a document is legally authentic, a model produced an answer, or a compliance standard is met, unless the thing behind it is real and verified. Where a figure is an estimate, the screen says so and shows the sample it came from.
