Launch readiness

Where ONEPASS actually stands for an India-wide launch, split so that what is finished is not confused with what is waiting on somebody.

The application is production-ready. The launch is not blocked on code. The production build was booted under NODE_ENV=production and exercised end to end: every public route, the whole signed-in consumer surface, the partner console and the platform console answered 200; /api/me/pass minted a live rotating token; CSS and JavaScript chunks loaded; tenant isolation still returned 404 to a consumer; and all 61 browser tests passed against that production server rather than a development one — including the real-time test, which admits a ticket in one browser and asserts that a door console in another updates on its own. That bundle carries no .env: every value came from the process environment, which is what makes it a build a host configures rather than one that carries a developer’s database inside it. What remains is infrastructure and third-party credentials, which are not ours to create.

India-wide by construction

Nothing scopes the product to a city. Cities are rows with an is_live flag; venues, offers and city passes hang off them; discovery, the planner and travel mode all read the live set. Opening Jaipur is a row and a partner, not a release. The last hardcoded assumption — the planner suggesting example prompts that named Pune — now generates its examples from whichever cities are live, so a person in a new city is never shown three suggestions that would return nothing.

The India-first choices are deliberate and sit in one layer: rupees as integer paise, Asia/Kolkata for every "today", en-IN formatting, E.164 mobile numbers, and Razorpay as the payment rail with an adapter interface behind it.

Future phase — international

Not started, and deliberately not started. The seams that would carry it already exist — the payment provider is an interface with adapters, money is minor units with a currency column, locale is a profile field, and cities carry their own timezone — but no second currency, tax model, provider or locale catalogue has been built, and building them now would be carrying weight before there is a market to carry it for.

03

The three domains, and why they are roles

The brief asked for three separate databases. What was built delivers the requirement — least privilege, service-level boundaries, no omnipotent connection — without the cost that three physical databases would have imposed.

ONEPASS’s core rows are relationships between a consumer and a business. A booking references both. A transaction references both. Split across three databases, every one of those foreign keys becomes an application-level join: referential integrity is gone, “take the seat, charge the card, issue the ticket” can no longer commit atomically, and the boundary moves into application code — which is exactly where the same brief says security must not live.

So the separation was built one layer lower, where application bugs cannot reach it: three PostgreSQL roles with per-table grants, plus row-level security on the seventeen relationship tables, plus a consent-gated view as the only route from a business connection to a person’s identity.

ServiceRoleReachesCannot reach
Consumer API
/api/me/*		 onepass_consumer Their own identity, consents, bookings, tickets, receipts, warranties, rewards, savings; the public catalogue read-only RBAC tables · API keys · webhooks · another person’s rows
Partner API
/api/partner/[org]/*		 onepass_business Its own venues, capacity, offers, staff, bookings, receipts, returns — filtered by RLS to its own tenant users · sessions · devices · payment_methods · audit_logs · security_events — no grant at all
Admin API
/api/admin/*		 onepass_admin RBAC, audit, security, platform config; read across the rest Cannot edit or delete the audit trail — INSERT only, for every role
The seam is real. Set DATABASE_URL_CONSUMER, _BUSINESS and _PLATFORM and the separation is live; leave them unset and everything shares one connection. isolationStatus() reports which mode is actually running rather than assuming — and if you later want three physical instances, these grants are the split line, so it becomes a migration rather than a redesign.
05

The Suspicious Activity Shield

Four detectors, one writer, and a refusal that shaped the rest of it.

The refusal. “Impossible travel” is conventionally built from IP geolocation: take the address on this sign-in, take the address on the last one, look both up with an IP-intelligence vendor. ONEPASS cannot do that, and should not be made able to. Every address in this system is stored as ip_hash — a peppered one-way hash — precisely so a database leak yields correlation inside these tables and nothing that points at a street. Adding a column that could be geolocated would trade a real privacy property for a feature.

So travel is computed from pass_presentations joined to venues.latitude/longitude — the places a pass was actually presented. That is better evidence than an address: a scan is a physical event at a known point, where an IP is a guess about a network. It also needs no vendor, no contract and no egress.

Building it surfaced a gap in the data. A presentation recorded only the organization, because a door console authenticates as one — so a chain with branches in Pune and Mumbai produced two scans that could have happened at either, and the detector could not tell a journey from a re-scan. The honest fix was to record the door: pass_presentations.venue_id is new, nullable because an organization-wide API key legitimately has no venue, and the detector handles both shapes.

DetectorWhat it measuresWhere it stays quiet
Impossible travel Haversine between scan locations ÷ elapsed hours. Above 900 km/h — a jet’s cruise speed, not below it — the pair is flagged Pune to Delhi in four hours is a flight, not an incident. Where a terminal named no venue, the slowest candidate pairing is used, so an ambiguous chain cannot manufacture an alert out of its own geography
Scan velocity The busiest 10-minute window per pass. Severity rises when the burst is mostly rejections — an accepted burst is a turnstile, a rejected burst is something trying codes Five scans across an evening is a person at a cinema
Device burst Distinct devices enrolled on one account within an hour Two in an afternoon is somebody replacing a phone. Device handles never appear in the evidence — a handle is an authenticator, not a label
Credential stuffing Failed sign-ins from one origin against many distinct accounts inside fifteen minutes. This is what ip_hash was built for: it cannot say where, but it groups perfectly, and the question is only “same origin” Ten failures against one account is someone who forgot their password, and the per-account lockout already covers it. A slow trickle across an afternoon is a shared office

What it will not do

The first draft exported lockAccount and unlockAccount. They worked, and they were wrong: PATCH /api/admin/users/[id] already suspends an account, revokes every session through the generation counter, notifies the person and writes the audit entry with the administrator’s reason. A second way to lock an account is a second set of rules about what locking means, and the first divergence between them would be discovered during an incident. They were deleted.

So detection files findings and stops. Response goes through the console’s existing path, where a human supplies the reason. A 900 km/h threshold should not be able to strand a real person at an airport on its own.

Findings go to one place

Into security_events, through recordSecurityEvent — the writer that already existed. No second security store, no SecurityEventV2: the console, the acknowledgement flow and the retention story are all built on that table. Every finding carries a deterministic fingerprint, and one already filed inside the window is not filed again, which is what makes a scheduled sweep safe. 

$ npm run security:scenario        # writes the three shapes, then runs the real detectors

found 4   written 3   already filed 1

  [MEDIUM] suspicious.impossible_travel
    Pass presented 126 km apart in 4 min — 1703 km/h implied.
    fromVenue "Grand Sahyadri — Koregaon Park"  toVenue "Grand Sahyadri — Bandra"
    distanceKm 126.3  elapsedMinutes 4.4  thresholdKmh 900
    located "both terminals named their venue"
    note "Computed from scan locations, not from IP addresses"

  [HIGH] suspicious.credential_stuffing

The scenario is a rehearsal, and says so. The seed trades normally and the detectors find nothing in it — which is the correct result and the honest empty state. Rather than bake a fake incident into the seed, npm run security:scenario writes the evidence a real incident would leave, tags every row it creates, clears the previous run so it is repeatable, and then lets the real detectors find it through the real code path.

This is the property that makes the verification API worth trusting: a database compromise cannot forge a credential, because the signature is over a hash of the claims and the issuer holds the key.

The flows, end to end

Both sides of one transaction, as the code actually runs it.

Consumer

  1. Register — email, optional mobile, Argon2id password. Identical response whether or not the address exists.
  2. Verify — six-digit code, hashed at rest, ten-minute expiry, five attempts.
  3. Pass issued — TOTP secret sealed with AES-256-GCM; the QR carries a reference and a rotating code, never personal data.
  4. Discover — live deals ordered by what expires soonest.
  5. Book — capacity held under a row lock for ten minutes; price derived server-side from the slot and the offer.
  6. Pay — one transaction on the sandbox rail; the browser’s word is never trusted.
  7. Confirm — seat sold, offer redeemed, saving recorded, points credited, ticket issued. One database transaction.
  8. Attend — the door admits the ticket exactly once.
  9. Keep — receipt with line items, warranty derived where applicable, return window open.
  10. Withdraw — revoking a consent removes the partner’s access on the next read.

Merchant

  1. Publish capacity — slots with a real count, list price and window.
  2. Read the advisor — findings computed from their own rows, each showing its method, sample size and evidence.
  3. Check demand — per-slot estimates with confidence; where history is thin it says so instead of guessing.
  4. Create a deal — discount rule in, computed price out; the deal cannot price below zero or exceed the slot.
  5. Take the booking — arrives in real time on the organization’s own channel.
  6. Admit at the door — once, with a readable reason on rejection.
  7. See the customer — through the consent view: a reference always, a name only if shared.
  8. Handle a return — explicit state machine; refunds capped at the units actually returned.
  9. Settle — cross-brand points reconcile at the issuer’s rate.

Where the defensibility actually is

It is not the QR code, and it is not the app. Three things compound:

The settlement graph. Once a cinema’s points are honoured at a restaurant and money moves between them, the relationship has a price attached and a switching cost. A competitor can copy the feature; they cannot copy the agreements.

Consent as an asset. A person who has granted a partner access has done something no scraped dataset replicates, and something that survives a privacy regime tightening. The k-anonymity floor and per-scope consent are not compliance theatre — they are what makes the audience durable.

Being the verifier of record. An issuer whose credentials are checked through ONEPASS, with the check recorded and visible to them, has a reason to keep issuing through it. That is a two-sided lock-in that gets harder to displace with every credential.

What is not a moat: the schema, the UI, the QR encoder. All copyable in a quarter. The moat is the graph, and the graph only exists once the loop runs for real.

Three minutes, to an investor

India’s physical commerce runs on a hundred separate identities. A hotel knows you; the cinema next door does not. You prove who you are at every counter, and every business rebuilds the same customer record from scratch — badly, and at their own cost.

ONEPASS is the layer underneath. One identity, presented with consent, verified in about a second. For the person: their tickets, receipts, warranties and points in one place, and a consent screen where withdrawing takes one tap. For the business: capacity that would have expired unsold, priced and distributed in minutes, and a customer record they did not have to build.

The wedge is unsold capacity, because it is the one thing every partner has and nobody monetises. A cinema seat at 19:01 is worth zero. At 18:30 it is worth ₹149 to someone who would not otherwise have come. We take a share of revenue that did not exist before we introduced it — which is why partners say yes.

The business is not the app. It is the settlement graph underneath: when a cinema’s points are spent at a restaurant, we settle between them, and every such agreement makes the network harder to leave. Add the verification API — priced per check — and the loyalty network becomes infrastructure rather than a feature.

What exists today is a working multi-tenant platform: 74 tables, 60 screens, tenant isolation enforced by the database rather than by application code, and 183 passing tests including the adversarial ones — 123 against a live Postgres and 60 driving a real browser. Payments run on a labelled sandbox until merchant credentials arrive — we are not pretending otherwise. What we need is a pilot: eight Pune partners, one city, one loop, running for real.

Three minutes, walking someone through it

Two browsers side by side: a person signed in as meera@example.in, merchant as owner@phoenix-cinemas.example. Password onepass-sample-password.

  1. Open the landing page. “These numbers are read from the database on every request. Five venues, seven live deals — the page cannot drift from the product.”
  2. Consumer → ONEPASS. “A rotating code. It carries a reference and a time-based code, never her name — so a photograph of this screen is worthless in thirty seconds.”
  3. Live Deals. “Ordered by what expires soonest. Forty seats at Phoenix tonight, ₹149 against ₹300. That seat is worth nothing at 19:01.”
  4. Book it. Capacity is held under a row lock. “Twenty-five people going for ten seats: exactly ten get one. We have a test that does that.”
  5. Confirmation. “One transaction: seat sold, offer redeemed, ₹151 saved, points credited, ticket issued. There is no state where three of those five are true.”
  6. Receipts → warranty. “The kettle carries a 24-month warranty, derived at issue. The return window is stored on the receipt, so a policy change tomorrow cannot close it.”
  7. Savings. “A sum of rows, each pointing at the purchase that caused it. Not a number we chose.”
  8. Switch to Merchant OS → Insights. The moment. “Tuesday revenue is 54% below the weekly average. Nobody told it about Tuesday — it computed that from 57 trading days, and here is the evidence table it used.”
  9. Demand. “96% confidence where there are eight matching windows. And here — no history, so it says this is a placeholder, not a forecast, rather than inventing one.”
  10. Create a deal from the suggestion. The form pre-fills from the forecast. The consumer’s Live Deals shows it.
  11. Door console. Admit the ticket. Scan again: Already used. “Six simultaneous scans admit exactly once — the check and the write are one statement.”
  12. Customers. “A reference always. A name only where she granted it. Contact is separately withheld — identity consent does not imply contact consent.”
  13. The isolation test. Change the org id in the URL. 404. “Not 403 — a 403 would confirm it exists. And below that, the business role has no grant on the users table at all.”
  14. The tamper test. Edit a credential’s claims in psql. Refresh /v/[ref]: Invalid. “A database compromise cannot forge a credential.”
  15. The Shield. Platform console → Security → Sweep the last 3 hours. “One pass, 126 km apart, four minutes: 1,703 km/h.   16. The planner. “Saturday evening in Pune for two, under ₹2,000, food and a film.” It shows what it understood before it shows the plan, and each item says why it is there in that item’s own numbers. Then ask for the impossible: it names the constraint that stopped it instead of quietly returning less.

Done since the last report

  1. Browser end-to-end tests. 60 Playwright tests across nine specs — consumer, partner, admin, public, PWA, isolation, auth, support and security. They caught a route collision that made the consumer home dead code, and the agent that found it correctly refused to weaken the assertion.
  2. The admin console. Ten screens. Partner approval, user suspension, the audit trail, the security queue and the support queue no longer need psql.
  3. The remaining features have screens. Split, gifts, city pass, quests, the planner and travel mode all render live rows. Support gained the intake the table never had, and the console gained the state machine.
  4. The anomaly detector. Written, tested and wired to a button on the security console — see section 05.
  5. CI and containers. Two GitHub workflows, a multi-stage Dockerfile, a compose stack and two deployment documents.
  6. The two missing public pages. /developers and /pricing were linked from the landing header, the landing footer and the notice on /verify, and every one of those links 404’d. Both are now written from the routes themselves — the request shape, the outcome union, the rate limit and the error envelope are read off the code rather than described.
  7. The delivery guard closed. SES and Twilio no longer pass the production boot check, and RESEND and MSG91 now require their credentials — see below.
  8. The console sidebar. .navlink is an anchor with no display, so inside a plain-block .sidebar-group the links flowed inline: measured at 1440px, “Transactions” ran from x=264 to x=370, past the 272px column and across the page heading. The group is a flex column now, and the block rule is scoped to the sidebar because the topbar genuinely is a row.
  9. A native client, scoped to what needs one. mobile/ is an Expo app that signs in and shows the rotating pass — not a second copy of two dozen screens. It reuses @onepass/pass/qr, so there is still exactly one QR encoder in the repository. Verified as far as this environment allows: typecheck clean, the Android bundle exports, and the web bundle renders in a browser. No device build, no store submission, and NFC is named rather than stubbed.

What is still open, and what would bite first

  1. The committed migrations are stale. 74 tables in the schema, 35 in drizzle/*.sql — the 39 commerce and extension tables have no migration, so npm run db:migrate leaves an unusable database. drizzle-kit push is the working path and is what bootstrap and CI use. This wants fixing before anyone deploys from the migration folder.
  2. drizzle-kit push drops the row-level security policies. Observed, not theorised — a push removed all 34 policies and isolation.sql had to be re-applied. Bootstrap does this in the right order; anyone pushing by hand must remember to. It also cannot tell a renamed column from a dropped one, and stalls waiting for an answer --force does not give — venue_maps.is_demo → is_sample was applied as an explicit ALTER.
  3. The Docker image has never been built. This environment cannot reach a container registry, so every COPY, the non-root switch and the healthcheck are unexecuted and the base image tag is unverified. The standalone bundle itself was built and run, and its health endpoint answered.
  4. No ESLint configuration exists. npm run lint drops into interactive setup and exits 1. Typecheck and both test suites are clean; lint is simply not set up.
  5. The native shell is unproven. The mobile JS bundles and renders, but with no Android SDK and no Xcode here, expo run:android has never executed and NFC is not implemented. Nothing claims otherwise.
Two seeds were silently lying, and both are fixed. seedSampleData and the credential seed were idempotent by identity — one row per sample person, one organization per slug — which quietly meant that anything written at creation was never revisited. So changing the shared sample password updated the banner the seed prints and nothing else, and every sample sign-in failed against a correct-looking password; and renaming the sample issuer left the old name inside a signed credential that the public verification API went on returning. Both seeds now correct what they find: the password is re-hashed to the constant it advertises, the organization is renamed in place, and the credential is re-issued rather than duplicated. A seed that drifts from the data it claims to produce is worse than no seed, because it looks like it ran.
One thing to fix before any deployment. The development seed uses a shared password across every sample account and prints it to the console. That is correct for development and would be a breach in production — seedSampleData refuses to run in production without an explicit override, and it should stay that way.
